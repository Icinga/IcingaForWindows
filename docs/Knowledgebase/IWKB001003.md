# Icinga Knowledgebase - IWKB001003

## Short Message

One of the following messages is reported:

```text
[UNKNOWN] Missing required macro "ifw_api_command" for Icinga CheckCommand "<CheckCommand>". Ensure the CheckCommand imports "ifw-api" and defines "vars.ifw_api_command" (IWKB001003)
```

```text
[UNKNOWN] Missing required macro "ifw_api_command" in ExecuteCommand payload. Ensure the CheckCommand imports "ifw-api" and defines "vars.ifw_api_command" (IWKB001003)
```

```text
[UNKNOWN] Binary command path "<Path>" contains invalid path characters or is outside "C:\ProgramData\IcingaForWindows\Binaries" (IWKB001003)
```

```text
[UNKNOWN] Binary command path "<Path>" could not be normalized inside "C:\ProgramData\IcingaForWindows\Binaries" (IWKB001003)
```

```text
[UNKNOWN] Binary command path "<Path>" is outside the approved Icinga for Windows binaries directory "C:\ProgramData\IcingaForWindows\Binaries" (IWKB001003)
```

```text
[UNKNOWN] Check command "<Command>" could not be resolved as an "Invoke-IcingaCheck*" PowerShell plugin or as an executable inside "C:\ProgramData\IcingaForWindows\Binaries" (IWKB001003)
```

---

## Cause

`IWKB001003` is raised whenever `Resolve-IcingaProtocolCommand` cannot safely resolve the command requested by Icinga 2. There are three distinct causes:

### 1. Missing `ifw_api_command` Macro (e.g. Unmodified ITL Commands like `load-windows`)
Standard Icinga Template Library (ITL) commands such as `load-windows`, `disk-windows`, or `ping-windows` use `import "plugin-check-command"` (`methods_execute = PluginCheck`). When scheduled against an Icinga for Windows endpoint without `import "ifw-api"` on the `CheckCommand`, Icinga 2 only sends `"command": "load-windows"` with an empty `"macros": {}` block. For security and predictability, Icinga for Windows never guesses executables from `params.command` and requires `macros.ifw_api_command`.

### 2. Invalid Path Characters, NTFS Alternate Data Streams, or Path Outside `C:\ProgramData\IcingaForWindows\Binaries`
`macros.ifw_api_command` contained ASCII control characters (`0x00..0x1F`), NTFS Alternate Data Stream colons (`check_load.exe:stream`), drive-relative paths (`C:tool.exe`), an absolute path (such as `C:\Windows\System32\cmd.exe`), a UNC path, or relative parent traversal (`..\`) pointing outside the approved `Get-ModuleBinaryDirectory()` folder (`C:\ProgramData\IcingaForWindows\Binaries`). Icinga for Windows never executes binaries from `$env:PATH` or arbitrary filesystem locations.

### 3. Command Does Not Match an Installed Plugin or Approved Binary
`macros.ifw_api_command` was provided, but:
- No matching file (`.exe`, `.cmd`, `.bat`, `.com`, `.ps1`) exists inside `C:\ProgramData\IcingaForWindows\Binaries`, **and**
- Neither the name itself nor its shorthand expansion (`Invoke-IcingaCheck<Name>`) matches a loaded `Invoke-IcingaCheck*` PowerShell function (or it attempted to invoke a non-check cmdlet such as `Get-Process` or `Remove-Item`).

---

## Solution

### Running a PowerShell Check Plugin
1. Ensure the check plugin is part of Icinga for Windows (or an installed check component exporting `Invoke-IcingaCheck*`).
2. Import `ifw-api` on the `CheckCommand` and set `vars.ifw_api_command` to the plugin name (for example `"Invoke-IcingaCheckCPU"` or shorthand `"cpu"`).

### Running an External Binary or ITL Plugin Executable
1. Copy the required binary (for example `check_load.exe`) into **`C:\ProgramData\IcingaForWindows\Binaries\`** on the Windows endpoint.
2. Create or update the **`CheckCommand`** object in Icinga 2 DSL or Icinga Director so that it imports **`ifw-api`** (not just on the Service, but on the `CheckCommand` itself!) and sets `vars.ifw_api_command` to the binary filename:

```icinga2
object CheckCommand "ifw-load-windows" {
    import "ifw-api"

    vars.ifw_api_command = "check_load.exe"

    arguments = {
        "-w" = {
            value = "$load_win_warn$"
        }
        "-c" = {
            value = "$load_win_crit$"
        }
    }
}
```
