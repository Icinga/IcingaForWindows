# Icinga Knowledgebase - IWKB001000

## Short Message

```text
[UNKNOWN] Unable to map Custom-Variables to Icinga for Windows Check "<CommandName>": <VariableList> (IWKB001000)
```

---

## Cause

Icinga 2 executed a PowerShell check command on Icinga for Windows **without** an active `ifw_api_arguments` argument mapping dictionary (meaning the `ifw-api` template was not imported on the `CheckCommand` definition), and one or more custom variables attached to the Host or Service could not be matched to any parameter of the target PowerShell check plugin.

Because Icinga for Windows does not parse local Icinga 2 `.conf` files on the monitored Windows agent, it relies on one of two mechanisms to map Icinga custom variables to PowerShell parameters:

1. **Recommended (`ifw-api` active on the `CheckCommand`):** Icinga 2 transmits `macros.ifw_api_arguments`, explicitly mapping each CLI/cmdlet parameter (such as `-Path`) to its Icinga macro (`$my_custom_var$`), regardless of how your custom variables are named.
2. **Fallback (`ifw-api` inactive):** When `ifw_api_arguments` is absent, Icinga for Windows can only bind custom variables whose names match either:
   - An **exact parameter or alias name** of the PowerShell check plugin (for example `vars.Path = "C:\\Logs"`), or
   - The **standard Icinga for Windows naming pattern** `IcingaCheck<CheckName>_<DataType>_<ParameterName>` (for example `vars.IcingaCheckDirectory_String_Path = "C:\\Logs"` for `Invoke-IcingaCheckDirectory`).

Any other custom variable (for example `vars.custom_folder = "C:\\Logs"` or an unrelated variable forwarded without `ifw-api`) cannot be unambiguously assigned to a PowerShell parameter and triggers `IWKB001000`.

> **Note on Host `vars` in Fallback Mode:** When `ifw-api` is not imported on the `CheckCommand`, Icinga 2 may include general Host custom variables (such as `host.vars.os = "Windows"` or `host.vars.location`) inside `macros`. While internal `ifw_api_*`, `IcingaPowerShellBase_*`, and empty `""` placeholder keys are ignored automatically, arbitrary Host `vars` do not match check plugin parameters and will trigger `IWKB001000`. Importing `ifw-api` on the `CheckCommand` scopes parameter resolution strictly to `ifw_api_arguments` so Host metadata variables never interfere.

---

## Solution

### Option 1 (Recommended): Import `ifw-api` on the `CheckCommand`

Import the `ifw-api` template directly on the **`CheckCommand`** object (not on the `Service` object) in Icinga 2 DSL or Icinga Director so Icinga 2 sends `ifw_api_arguments`:

```icinga2
object CheckCommand "Invoke-IcingaCheckDirectory" {
    import "PowerShell Base"
    import "ifw-api"

    vars.ifw_api_command = "Invoke-IcingaCheckDirectory"

    arguments += {
        "-Path" = {
            value = "$IcingaCheckDirectory_String_Path$"
        }
        "-Warning" = {
            value = "$IcingaCheckDirectory_String_Warning$"
        }
        "-Critical" = {
            value = "$IcingaCheckDirectory_String_Critical$"
        }
    }
}
```

In **Icinga Director**, re-import the current Icinga for Windows Director Basket or add `ifw-api` under **Commands -> Commands -> `<Your CheckCommand>` -> Imports**, then deploy the configuration.

### Option 2 (Fallback without `ifw-api`): Use Exact Parameter Names or the Standard Naming Convention

If you intentionally execute PowerShell checks without importing `ifw-api`, rename the custom variables on your Host/Service so every check variable matches either the exact parameter name or `IcingaCheck<CheckName>_<DataType>_<ParameterName>`:

```icinga2
apply Service "Directory Check" {
    check_command = "my-custom-directory-command"
    vars.ifw_api_command = "Invoke-IcingaCheckDirectory"
    vars.Path            = "C:\\Backup"
    vars.Critical        = "0"
    assign where host.vars.os == "Windows"
}
```
